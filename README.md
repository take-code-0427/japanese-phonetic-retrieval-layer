# Japanese Phonetic Retrieval Layer

LLM が弱い「音韻空間」を、外部の検索システムとして提供する。

**デモ: https://japanese-phonetic-retrieval.fly.dev**
(SudachiDict core / 111 万語。full の 202 万語はローカルで構築できる)

LLM は意味的類似性には強いが、「音として似ている」という関係を明示的に扱うのが
苦手だ。たとえば **乳首** と **チョコビ** は意味的にはほぼ無関係だが、発音上は
一定の類似性がある。人間はなぞなぞ・ダジャレ・空耳・聞き間違いの文脈でこの
音韻的類似を自然に利用するが、semantic embedding ではこの関係を検索できない。

このプロジェクトは意味検索に対する semantic embedding、画像に対する vision
embedding と同様に、**音韻に対する retrieval** を提供する。

```
Semantic RAG : 意味の近い知識を取ってくる
Phonetic RAG : 音の近い語を取ってくる      <- これ
```

## 仕組み

オフラインで辞書全体を音韻ベクトル化しておき、実行時は入力語だけを
ベクトル化して近傍検索する。

```
オフライン:
  SudachiDict (288 万語)
      -> 読み (カタカナ)
      -> 音素列 / モーラ列
      -> phonetic embedding (索引に載せるのは 3 空間)
      -> NumPy 行列 (音素列グループごとに 1 行 / mmap で読む)

オンライン:
  入力語 -> 読み -> 音素列 -> embedding
      -> 索引全体と内積を取り上位 K 件            ... 速度をここで稼ぐ
      -> weighted phonetic edit distance で rerank  ... 精度をここで稼ぐ
      -> 最終 Top-N
```

embedding だけに任せないのは「なぜ近いのか」が曖昧になるためだ。ダジャレ用途
ではモーラ数が同じ・語尾が一致・子音だけ違う・母音列が似ているといった局所的な
構造が効くので、最終スコアはそれらを明示的に重み付けして決める。

**ANN (HNSW) は使っていない。** hnswlib はグラフをメモリに実体化し、しかも同じ
ベクトルを内部に複製するので 620MB を消費した (2GB のホストが OOM で落ちた)。
総当たりなら索引を mmap で読むだけなので**メモリが 1/150 になり、再現率も 0.986
から 1.0 に上がる**。代償は速度で、202 万語では中央値 14ms から 40ms に落ちる
(111 万語なら 11〜16ms で ANN と同等)。メモリと速度の交換であって無条件に
優れた選択ではないので、詳細は `CLAUDE.md` に実測値付きで残してある。

### 入力の長さで経路が変わる

上の経路は **1 語を 1 語に写す**。だが長い入力に音が近い単一の語は辞書に存在
しない — 「ワタシノナマエハ」(8 モーラ) に相当する 1 語は無いので、いくら候補数を
増やしても答えは返らない。長い入力には**語を組み立てる**経路を使う。

```
1 語 -> 1 語         乳首              -> 手首 / チョコビ        (`similar`)
1 句 -> 語 + 助詞     ワタシノナマエハ    -> 私 | の | 名前 | は    (`phrase`)
```

後者は入力をモーラ境界で区間に切り、区間ごとに音の近い語を当ててビーム探索で
繋ぐ。空耳・替え歌がこれにあたる。

### 音素距離

音素を記号ではなく音声学的素性のベクトルとして扱う。

```
/k/  [-voiced, velar, stop]
/g/  [+voiced, velar, stop]     -> 有声性のみの差なので距離は小さい (0.14)
/m/  [+voiced, bilabial, nasal] -> 調音位置と方法まで違うので大きい (0.69)
```

子音は調音位置・調音方法・有声性・口蓋化、母音は舌の高さ・前後・円唇性から
距離を導き、weighted Levenshtein で音素列間の距離を計算する。

### 5 つの埋め込み空間

用途によって「近い」の定義が変わるので、単一のベクトルに混ぜず別々に持つ。

| 空間 | 内容 | 効く場面 | 索引 |
|---|---|---|---|
| `phonetic` | 全体の音韻 | 既定の候補生成 | ○ |
| `coda` | 語尾 2 モーラ | 韻、語尾の一致 | ○ |
| `vowel` | 母音の骨格のみ | 韻を踏む語 | ○ |
| `consonant` | 子音の骨格のみ | 母音が違っても子音が揃う語 | — |
| `rhythm` | モーラ数と特殊モーラの配置 | リズムの近さ | — |

索引に保存するのは検索が実際に読む 3 空間だけ。`consonant` と `rhythm` を引くのは
`compare` (2 語の比較) で、あちらは索引を引かず入力をその場で埋め込むため行列が
要らない。

素性は位置ビンに分けて畳み込むので語順が保たれる (「チクビ」と「ビクチ」は
別のベクトルになる)。ビンの粒度は全体と前後半のマルチスケールにしている。
細かく割ると語頭 1 音素の差でビンが丸ごと外れ、「チクビ」と「テクビ」の
類似度が 0.68 まで落ちて 候補の上位にすら入らなかった。細かい位置合わせは
rerank 段の編集距離が担うので、候補生成側は粗くてよい。

### 用途別プリセット

```
pun         ダジャレ・なぞなぞ。音韻全体の近さと、知られた語であることを重視
rhyme       韻を踏む語。語尾と母音列を重視し、語頭の一致は求めない
mishearing  聞き間違い・ASR 補正。全体の音韻とリズムの一致を最重視
```

### 実測 (SudachiDict full / 202 万語)

```
索引構築    約 11 分 (辞書走査 173s + 埋め込み 460s)
索引サイズ  322MB (ベクトル 3 空間 188MB + 語彙メタデータ 133MB)
候補生成    内積 + Top-K 7.5ms (146 万グループ)
分割合成    3 モーラ 18ms / 8 モーラ 186ms / 14 モーラ 267ms
索引ロード  0.37 秒 (mmap)
常駐メモリ  15MB (索引を開いた直後) / 158MB (全走査まで通したピーク)
```

**行は語ではなく音素列グループ。** 埋め込みも編集距離も音素列だけの関数なので、
同音異表記 (「価格」「架格」「カカク」) は同じベクトルと同じ距離を持つ。行ごとに
持つと 202 万行のうち 146 万ぶんしか情報が無いのに全部を保存し、内積も重複して
計算することになる。グループ単位にすると行が 28% 減り、索引サイズと内積の両方に
効く (内積 + Top-K は 10.3ms → 7.5ms)。候補数 8000 の意味も
「**異なる音素列**を 8000 個」に変わるので、上位が同じ音の異表記で埋まらない。

**索引に持つのは検索が読む 3 空間だけ** (`phonetic` / `coda` / `vowel`)。
`consonant` と `rhythm` を引くのは `compare` だけで、あちらは索引を引かず入力
2 語をその場で埋め込むため行列が要らない (5 空間ぶん保存していた頃は 107MB が
読まれないまま置かれていた)。

**語彙メタデータは npz にまとめず 1 配列 1 ファイルで置く。** npz は zip なので
mmap できず、`np.load` が 133MB をヒープに展開する。個別の `.npy` なら mmap で
開けて、同じ 133MB が回収可能なページキャッシュに移る。ディスク上の大きさは
変わらないが、**索引を開いた直後の匿名メモリが 149MB → 15MB になる** (2GB の
ホストで OOM に効くのはこちらの軸)。

候補数 (`--candidates`) を 400 に絞ればもう少し速いが、202 万語ではコサイン
0.91 以上の語が 400 件を超えるため、「乳首」に対する「手首」のような明らかな
近傍が候補から漏れる。既定は品質を優先して 8000 件にしている。内積は全行に
対して取るので、**候補数を増やしても重くなるのは rerank だけ**だ。

**ベクトルは int8 に量子化してある。目的はサイズで、速度ではない。** 索引が
1.64GB から 508MB になった (グループ化と 3 空間化を重ねて現在は 322MB)。
内積そのものは BLAS の float32 と互角で
(17〜29ms 対 15〜26ms)、読むバイト数が 1/4 になっても DRAM 帯域律速なので
速くならない。速度で得しているのは Top-K だけ (`argpartition` の 9〜16ms に対し
3〜10ms)。量子化の誤差は内積で最大 0.012 あり候補生成の順位をわずかに揺らすので、
候補数を 5000 から 8000 に広げて吸収している (float32 基準の再現率 0.919 → 0.997)。

HNSW をやめて総当たりにしたとき、候補生成は中央値 14ms から 31ms に落ちた。
その代わり索引が 4.1GB から 1.64GB になり、再現率が 0.986 から 1.0 になった
(2GB のホストで動かすための交換)。int8 量子化はさらに索引を 508MB まで縮めるが、
**速度はこの交換を取り戻さない** — 内積は帯域律速で BLAS と互角のままなので、
候補生成は ANN 時代より遅い。速度が要るなら ANN に戻す判断は依然として残る
(その場合はメモリを積む前提になる)。

編集距離は Rust (rayon で並列化) で計算する。53 万候補の rerank が NumPy 実装の
1097ms に対して 41ms で、26 倍速い。内積は「選んだ行だけを mmap から引く」のを
やめて全行と内積を取ってからマスクしている — 97 万行の選抜で 228ms が 16ms になる。
コストは演算ではなく飛び飛びに読んだ行の実体化にあるので、連続読みのほうが
対象が 2 倍あっても速い。

## インストール

```bash
uv sync --extra full        # Rust 拡張もここでビルドされる
uv run jpr build-index      # 初回のみ。10 分ほどかかる
```

**Rust ツールチェインが必要。** 編集距離を計算する拡張 (`rust/`) を `uv sync` が
maturin でビルドする。未導入なら [rustup](https://rustup.rs/) で入れる。

**`--extra full` は full 辞書 (202 万語) を入れる。** CLI の既定
(`--dict full`) と full 索引の構築に要る。core だけで足りるなら省ける —
`sudachidict-full` は 344MB あり、実行時にどちらを読むかは索引の `dict_type` が
決めるので、core の索引で動かすなら一度も読まれない (デプロイ用のイメージは
これを外してある)。省いた場合は `--dict core` を明示する。

索引は `~/.cache/jpr/index` に置かれる。

### モーラ長で絞り込む

既定の検索は音韻空間の近傍を引くので、上位はクエリと同じ長さの語で埋まる。
「もっと長い語」を見たいときは `--min-mora` / `--max-mora` で範囲を切る。

```console
$ uv run jpr similar 乳首 --min-mora 5 --max-mora 5 -n 5
モーラ範囲を指定 — 301,551 語を全走査します
乳首 -> チクビ [ch i k u b i] 3 モーラ  (1441ms, preset=pun)

 score     音韻     語尾    拍  語                読み             カテゴリ
 0.782  0.703  0.763    5  チン潜り             チンクグリ          common
 0.778  0.806  0.274    5  キングピン            キングピン          common
 0.776  0.809  0.271    5  チェックペン           チェックペン         product
 0.771  0.719  0.754    5  インシグネ            インシグネ          common
 0.765  0.810  0.423    5  シーキューブ           シーキューブ         product
```

範囲を指定すると **上位 K 件ではなく、その長さの語を全走査する**。既定は音韻空間の
Top-K を返すので、モーラ数の違う語はそもそも候補に入らないため (候補数を増やしても
届かない)。代償は速度で、1 つの長さあたり約 1 秒、3 つ分の範囲で約 4 秒かかる。

`-n 0` は件数無制限。スコア下限と組み合わせると「閾値を超えた語を全部」が得られる。

```bash
uv run jpr similar 乳首 --min-mora 5 --max-mora 5 --min-score 0.75 -n 0
```

その他のオプション:

```bash
uv run jpr similar 田中 --categories person   # 人名を明示的に引く
uv run jpr similar 地球儀 --preset mishearing  # ASR 補正向け
uv run jpr similar 乳首 --json
uv run jpr similar 乳首 -k 20000              # 候補数を増やして再現率を上げる
```

### 長いフレーズを語の連なりに置き換える (空耳)

`similar` は 1 語を 1 語に写すので、長い入力には答えが返らない — 8 モーラの
「ワタシノナマエハ」に音が近い**単一の語は辞書に存在しない**。人が空耳を作るときは
入力を区切って別々の語を当てているので、`phrase` はその操作をそのまま行う。

```console
$ uv run jpr phrase わたしのなまえは -n 3
わたしのなまえは -> ワタシノナマエハ /w a t a sh i n o n a m a e h a/ [wataɕinonamaeha] 8 モーラ  (272ms)

 0.746  私の名前は   [ワタシノナマエハ]
        ワタシ→私(1.00) | ノ→の(1.00) | ナマエ→名前(1.00) | ハ→は(1.00)
 0.743  棉白名前は   [ワタシロナマエハ]
        ワタ→棉(1.00) | シノ→白(0.94) | ナマエ→名前(1.00) | ハ→は(1.00)
 0.743  棉篠名前は   [ワタシノナマエハ]
        ワタ→棉(1.00) | シノ→篠(1.00) | ナマエ→名前(1.00) | ハ→は(1.00)
```

2 行目が「入力のどこが何になったか」で、括弧内はその区間の音韻類似度。空耳は
対応が読めないと検証できないので、表層だけでなく区間の対応を必ず返す。

```console
$ uv run jpr phrase こんにちはせかい -n 2
 0.815  今日は世界   [コンニチハセカイ]
        コンニチ→今日(1.00) | ハ→は(1.00) | セカイ→世界(1.00)
 0.812  今日端会   [コンニチハシカイ]
        コンニチ→今日(1.00) | ハセ→端(0.91) | カイ→会(1.00)
```

仕組みは 3 段。入力のモーラ列を区間に切り (モーラ境界のみ — 音素の途中で切ると
どちらも発音できない断片になる)、区間ごとに**同じモーラ数の語**を編集距離で
照合し、ビーム探索で繋ぐ。繋ぎの助詞 (の・を・に・が・は…) は内蔵の表から引く:
索引は助詞を落としているうえ 1 モーラの語を 1 件も持たないので、この表が無いと
1 モーラの区間が埋まらない。

速度は入力の長さに応じて 2 モーラ 4ms・8 モーラ 186ms・14 モーラ 267ms
(2.02M 語, 暖まった状態)。

```bash
uv run jpr phrase ありがとうございます --max-chunk 5   # 1 区間に長い語を許す
uv run jpr phrase わたしのなまえは --beam 64          # 探索幅を広げて取り逃がしを減らす
uv run jpr phrase わたしのなまえは --no-particles      # 助詞を使わない
uv run jpr phrase わたしのなまえは --json
```

#### 候補を 1 枚の図に畳む (ラティス)

候補を並べると同じ語が何度も出る。上の例でも「名前」「は」が全候補に現れていて、
実測では**表示している区間の 65〜77% が重複**していた。Web の「分割合成」タブで
**ラティス**を選ぶと、同じ語を 1 つのノードに畳んで分岐だけを見せる。

```
  [ 私 ]  ─────────┐
  (ワタシ)          │
                    ├─ [ の ] ── [ 名前 ] ── [ は ]
  [ 棉 ] ─ [ 白 ] ──┤    (ノ)     (ナマエ)     (ハ)
  (ワタ)   (シノ)    │              x12         x12
  [八咫] ─ [ 篠 ] ──┘
  (ワタ)   (シノ)
```

ノードの下に**入力側の読み**が付くので、どこを覆っているかが分かる。同じ語が
1 度しか出ないため「どこで枝が分かれ、どこから先は共通か」が読める。上の例では
12 経路が「名前」「は」を共有し、違うのは前半だけだと分かる。

ノードにカーソルを当てるとその語に繋がる辺だけが光る。押すとその語を通る経路に
絞られ、下に読み方が並ぶ。ノードの濃さと辺の太さは「そこを通る経路の数」で、
よく使われる語が目に入る。

**横軸はモーラ位置ではない。** 位置に幅を比例させると 1 モーラの語が 78px しか
取れず、隣の列が遠くに離れて辺の行き先が読めなかったので、列の幅は中身が要る分
だけ取って上下の位置合わせは捨てている。

ノード数は予算で抑える (既定 40)。**予算に届くまでビーム幅を広げる** ので、
上位数件だけでは構造が薄く全候補では埋まるという両極を避けられる。API は
`/api/phrase/lattice`。

### 読みと音素列を見る

```console
$ uv run jpr pronounce 東京特許許可局
東京特許許可局 -> トウキョウトッキョキョカキョク [t o u ky o u t o Q ky o ky o k a ky o k u] モーラ: ト ウ キョ ウ ト ッ キョ キョ カ キョ ク (11)
```

### Python から

```python
from jpr import PhoneticSearcher, PhoneticStore, default_store_path

searcher = PhoneticSearcher(PhoneticStore(default_store_path()))
pronunciation, results = searcher.search("乳首", preset="pun")

for result in results:
    print(result.surface, result.score, result.phonetic_similarity)
```

意味的な制約を掛けたい場合は `candidate_filter` を使う。

```python
snacks = {"チョコビ", "チョコボール", "ハイチュウ", "ウマイボウ"}
_, results = searcher.search(
    "乳首", candidate_filter=lambda entry: entry.reading in snacks
)
# -> チョコビ (0.808) が 1 位
```

長いフレーズは `compose`。区間ごとの対応が `segments` に入る。

```python
_, candidates = searcher.compose("わたしのなまえは", limit=5)

for candidate in candidates:
    parts = " | ".join(
        f"{s.source_reading}->{s.surface}" for s in candidate.segments
    )
    print(candidate.score, candidate.text, parts)
# -> 0.746 私の名前は  ワタシ->私 | ノ->の | ナマエ->名前 | ハ->は
```

同じ経路集合を DAG で受け取るには `lattice`。同じ語が 1 ノードに畳まれる。

```python
_, graph = searcher.lattice("わたしのなまえは", node_budget=12)

for node in graph.nodes:
    print(f"[{node.start}:{node.end}] {node.surface} x{node.path_count}")
# -> [0:2] 棉 x4 / [0:3] 私 x1 / [4:7] 名前 x12 / [7:8] は x12 …
```

```bash
uv run jpr serve
```

Claude Code に登録する場合:

```bash
claude mcp add jpr -- uv run --project /path/to/this/repo jpr serve
```

提供する tool:

| tool | 用途 |
|---|---|
| `search_phonetically` | 音が近い語を検索する (1 語 → 1 語) |
| `compose_phrase` | 長い入力を語 + 助詞の連なりに置き換える (空耳) |
| `compare_phonetically` | 2 語の音韻類似度を計算する |
| `pronounce` | 読み・音素列・モーラ構造を返す |

長いフレーズには `compose_phrase` を使う。`search_phonetically` に渡しても、
音が近い単一の語が辞書に無いので答えが返らない。

## 意味と音は別の軸

これが設計上もっとも重要な点だ。両者を混ぜない。

```
乳首 <-> バスト     semantic: 高い   phonetic: 0.05
乳首 <-> チョコビ   semantic: 低い   phonetic: 0.81
```

`semantic 低 + phonetic 高` はダジャレ候補のシグネチャになる。

ただし音韻空間だけでは答えが決まらないことに注意が必要だ。202 万語の辞書では
「乳首」に音韻類似度 0.82 以上の語が数百件ある。「乳首みたいなお菓子」の答えが
「チョコビ」なのは、それが音韻的に最も近いからではなく、**お菓子である**という
意味的制約が効くからだ。音韻検索は候補を出すところまでを担い、意味による選択は
呼び出し側 (LLM) が行う。

## 語彙カテゴリ

SudachiDict full は地名 49 万・人名 24 万を含み、索引の 7 割を占める。人名の
異表記 (「ココミ」に対する心々美・湖々美・瑚々海…) は音韻的に密集するので、
区別せずに検索すると一般語や商品名が上位から押し出される。

```
common   一般語 (普通名詞・動詞・形容詞)
product  商品名・作品名・組織名
person   人名     <- 既定では検索しない
place    地名     <- 既定では検索しない
```

## 実装メモ

- **辞書の列挙**: SudachiPy には語彙を列挙する API が無く (`lookup` は完全一致
  のみ)、Java 版の `dump` サブコマンドも提供されない。そのため `system.dic` の
  バイナリを直接パースしている (`dictionary.py`)。フォーマットの読み違いを黙って
  通さないよう、オフセットテーブルの整合性を起動時に検証する。
- **語の一般性**: 辞書には音が近いだけの稀語が大量にあるため、Sudachi の連接
  コストを反転させて「知られた語らしさ」の弱い指標として使っている。厳密な頻度
  ではないので、順位の同点をほどく程度の重みしか掛けていない。
- **索引形式**: pickle はロードに 12〜18 秒かかり MCP サーバの起動コストとして
  重すぎたため、NumPy 配列 (mmap) に移行した。文字列は固定幅 unicode 配列を避けて
  UTF-8 の可変長で持つ (`<U27` は最長要素の幅で全行を埋めるため、202 万語の表層
  だけで 218MB を消費していた)。
- **編集距離の高速化**: rerank では 1 クエリあたり数千件に編集距離を掛けるため、
  音素記号のまま扱うと Python の関数呼び出しが支配的になった。音素を整数 ID に
  落として置換コストを行列に事前計算し、DP の行を NumPy 演算にしている。
  ただし音素列は 3〜24 要素しかないので、1 件ずつ NumPy を呼ぶと今度は呼び出しの
  オーバーヘッドが実計算を上回った (1 件 80μs、2000 件で 190ms)。候補をバッチ軸に
  取って DP の 1 行を全候補について同時に進めると、同じ 2000 件が 9ms で終わる
  (22 倍)。これで 1 クエリ平均 440ms が 19ms になった。
  以前あった打ち切り (編集距離を除いた成分でスコアの上限を求め、上位が確定した
  時点の最低スコアを超えない候補には距離を計算しない) は、バッチ化で 1 件あたりが
  4μs に落ちたことで判定コストのほうが高くなったため外した。
- **上位だけを実体化する**: `store.entry()` は 1 件ごとに Python オブジェクトを作るので
  全候補に対して呼ぶと 2000 件で 40ms かかる。スコアは配列で全件求めた上で、
  `SearchResult` に起こすのは上位数十件だけにしている。同音異表記を畳んだ後に
  要求件数へ届かなければ、選抜幅を広げて起こし直す。
- **同音異表記の代表選び**: SudachiDict では読みをそのまま書いたカタカナ見出し
  (「カカク」cost 3269) が漢字表記 (「価格」cost 5496) より低コストなことがある。
  コストだけで代表を選ぶと「科学」の近傍が「カカク」になり語として何を指すのか
  読み取れないので、見出しの情報量を優先している。

## デプロイ (Fly.io)

`Dockerfile` と `fly.toml` を同梱してある。

```bash
fly launch --no-deploy   # 初回のみ (アプリ名とリージョンを確定する)
fly deploy
```

**索引はイメージに焼き込む。** Volume に置く案も採れるが、それだと「初回に
索引を用意する」手順がデプロイと別に要る。ビルド時に `build-index` を走らせれば
デプロイした時点で動く状態になる。

**辞書は core を使う** (`Dockerfile` の `--dict core`)。索引は **core が
855MB → 274MB (int8 量子化) → 148MB (グループ化 + 3 空間化)**、full は
1.64GB → 508MB → 322MB。実測で検索品質は保たれる — 「乳首」→ 手首、
「わたしのなまえは」→ 私の名前は が同じ順位で出る。

**メモリは 2GB (shared-cpu-1x の上限)。** イメージ内の実測 (`docker run -m 2g`、
core) は索引を開いた直後が匿名 19MB、全走査と分割合成まで通したピークが
**匿名 83MB + mmap 148MB**。モーラ範囲の全走査は並行度に比例して匿名メモリを
積むので (full の実測で 2 並行 +190MB・10 並行 +613MB)、`web.py` の
`MAX_CONCURRENT_SCANS` で全走査だけを 2 本に絞っている。既定の経路は軽いので
門を通さない。

**イメージは 641MB。** 内訳は venv 363MB (うち Sudachi の core 辞書 208MB) +
索引 142MB + Python の基底。`sudachidict-full` (344MB) は任意の依存に外して
ある — 実行時にどちらを読むかは索引の `dict_type` が決めるので、core の索引で
動かすこのイメージでは一度も読まれない。**次に大きいのは Sudachi の core 辞書**で、
読みの取得に要るので外せない。

以前 2GB で OOM killed になったのは ANN のグラフが 620MB を占めていたためで、
総当たりに移してからは余裕がある。`memory = '4gb'` は shared-cpu-1x では
受け付けられない (`cannot exceed 2048 MiB`)。

**`auto_stop_machines = "suspend"` + `min_machines_running = 1` で 0 台には
落とさない。** 落とすと次のリクエストが索引ロードを払う。

公開先の実測 (nrt / core 辞書):

| 経路 | 時間 |
|---|---|
| `/api/similar` | 22ms |
| `/api/similar` (5 モーラ全走査) | 570ms |
| `/api/phrase` | 432ms |
| `/api/phrase/lattice` | 55ms |
| `/api/pronounce`, `/api/compare` | 27〜34ms |

メモリは 2GB のうち `MemAvailable` 1699MB。プロセスの内訳は匿名 107MB +
mmap 143MB。索引を 274MB から 148MB に落としたぶん、空きが 949MB から
750MB 増えた。

Serverless (Vercel / Lambda 等) には載らない。ただし**理由からサイズは外れた** —
core の索引は 148MB になり、関数のデプロイ上限 (250MB) を下回っている
(以前は 274MB で超えていた)。残るのは Rust 拡張のビルドと mmap 常駐という
2 つの前提で、こちらはコンテナを要求する。
